# Что делает оригинальное приложение при запуске цикла

Разбор по декомпилированному коду — под вопрос «машина стартует, потом долго
пикает и останавливается». Все адреса ведут в [`../decompiled/dart/`](../decompiled/dart/).

Короткий ответ: **запуск — это ровно один кадр `0x02`, и больше приложение не
делает ничего.** Ни подтверждения, ни второй команды, ни периодического
опроса, ни keepalive. Так что «недосказанной» команды, которой не хватает
стороннему клиенту, в протоколе нет — причину надо искать в состоянии машины
и в том, что происходит до старта.

---

## 1. Нажатие кнопки

`widget/pcm_main_screen.dart`, `_setWorkState` (`0x6715d0`) целиком:

```
showLoading(globalWaitingTitle)
await device.setWorkState(start, mode)
dismiss()
      ↳ при исключении: showErrorMessage() + dismiss()
```

Перед этим — только диалог подтверждения (`heatingExtractionTip` /
`onlyExtractionTip` / `heatingTip`) и, при низком заряде,
`lowBatteryHeatingWarning`. Оба чисто интерфейсные, в эфир ничего не уходит.

`model/device/pcm_device.dart`, `setWorkState` (`0x67176c`):

```
if (!start)        localState = standby
else if (mode==1)  localState = hotExtractioning
else if (mode==2)  localState = coldExtractioning
else if (mode==0)  localState = hotWatering
sendHandle(PcmBlePack.setWorkState(start, mode))
```

`localState` — оптимистичное состояние для UI, в кадр не попадает.

`model/device/pcm_device_comand_pack.dart`, `setWorkState` (`0x671818`) —
нагрузка ровно два байта: `[start, WorkMode]`.

Итого в эфир уходит один кадр, например для «нагрев + экстракция»:

```
7F 00 07 89 02 01 01
```

## 2. Чего в приложении НЕТ

Проверено поиском по всему декомпилированному коду:

* **нет периодических таймеров, которые что-либо шлют.** `Timer.periodic`
  встречается только в `redux/appoint.dart` (обратный отсчёт таймера в UI) и
  `pages/pcm/pcm_history_page.dart`; ни один из них не обращается к устройству;
* **нет повторного опроса состояния.** `readRealTimeData()` (`0x86b564`,
  отправляет `0x00`) вызывается ровно один раз — последней строкой
  `initConnect`. Дальше состояние приходит само, машина пушит его в FFF1;
* **нет ответа на нотификации.** `_onGetDeviceState` только разбирает пакет и
  обновляет UI, ничего не отправляя;
* **нет команды подтверждения или продолжения цикла.** Единственные записи во
  время работы — те, что инициировал пользователь.

## 3. Что происходит до старта

Единственное место, где приложение может повлиять на машину заранее, —
рукопожатие. `PcmDevice.initConnect` (`0x86b25c`), точная последовательность
с паузами:

```
discoverServices()
FFF0/FFF1 setNotifyValue(true)
requestMtu(105)
подписка на поток mtu
задержка 300 мс          ← Duration 0x493e0
setTime            0x04
задержка  40 мс          ← Duration 0x9c40, дальше везде та же
getTempSetting     0x15
задержка  40 мс
getDeviceWorkParam 0x17
задержка  40 мс
getAppointment     0x24
задержка  40 мс
getDeviceInfo      0x08
задержка  40 мс
getCups            0x06
задержка  40 мс
readRealTimeData   0x00
```

Обратите внимание: **`setTime` — единственная запись в рукопожатии**, всё
остальное чтение. И она идёт после паузы в 300 мс, а не сразу.

Записи дополнительно сериализованы мьютексом с минимальным интервалом 20 мс
между кадрами (`ec_kit/model/device/base_device.dart`, `writeData` `0x55f6cc`:
`20000` мкс от момента прошлой записи).

## 4. Как приложение узнаёт об отказе

Ошибка приходит в байте 5 нотификации `0x00`. `_onGetDeviceState`
(`0x866ca4`, ветка `0x867044`):

```
err = data[5]
если err == 0            -> ничего
если err == предыдущий   -> ничего            ← диалог показывается только на СМЕНУ кода
иначе:
    1 dryBurning          -> showTipDialog(5)
    2 batteryOverheating  -> showTipDialog(9)
    3 heatingShortCircuit -> showTipDialog(8)
    4 lowBatteryHot       -> showTipDialog(3)
  >=5 lowBattery          -> showTipDialog(2)
```

Тексты из локализации, номера кодов в них подтверждают нумерацию:

| Код | Ключ | Текст |
|---|---|---|
| 1 | `dryBurningTip` | The device is in a dry burning status |
| 2 | `batteryOverheating` | Device failed, code: 02. Please wait before operating |
| 3 | `heatingShortCircuitTip` | Device failed, code: 02. Please contact the customer service |
| 4 | `lowBatteryHotTip` | Low battery, please charge as soon as possible, code: 04 |
| 5 | `lowBatteryTip` | Low battery, please charge as soon as possible, code: 05 |

Ключевая деталь для отладки: **диалог срабатывает только когда код меняется**.
Если машина выставила ошибку на секунду и сбросила её обратно в 0, в оригинале
это можно не заметить вообще. Свой клиент должен логировать каждый кадр `0x00`,
а не только текущее значение.

## 5. Пищит машина, не телефон

Аудио в приложении (`util/audio_util.dart`: `dingdong.mp3`, `didi.mp3`,
`bugu.mp3`, `bibi.mp3`) используется только из `redux/appoint.dart`,
`pages/reserve_page.dart` и `pages/pcm/pcm_reserve_page.dart` — это напоминание
**отложенного запуска**. На завершение или отказ цикла приложение не звучит
никогда.

Значит длинный писк — сигнал самой машины, и он либо про завершение цикла,
либо про ошибку. Различить их можно только по байтам 4 и 5 в `0x00`.

## 6. Найденная причина: установка температуры идёт в Фаренгейтах

Симптом с реальной машины: `0x15` вернула границы `100 … 204` и текущую
установку `91`, при текущей температуре `33`. В одних единицах эти три числа
не живут — и в коде видно почему.

**Машина держит установку температуры в °F, а текущую температуру отдаёт в °C.**

* `_onGetTempSetting` (`0x8665a4`) кладёт `data[0..2]` в min / max / установку
  **без преобразования**;
* `_onGetDeviceState` (`0x866ca4`, район `0x866e84`) берёт `data[3]` и считает
  `round(data[3] * 1.8 + 32)` — переводит **из °C в °F** — и только потом
  сохраняет. Значит внутри приложение целиком в °F, а провод в `0x00[3]` — °C;
* `presetTemperatureDisplay` (`0x572cdc`) и `currentTemperatureDisplay`
  (`0x609400`) делают обратное `round((x - 32) / 1.8)`, когда выбран Цельсий;
* `_DeviceSetPageState._save` (`0x658f58`, район `0x6591c8`) при выбранном
  Цельсии переводит значение пикера `round(x * 1.8 + 32)` **из °C в °F** и
  только потом зовёт `setTempSetting`.

Пересчёт наблюдаемых чисел: границы `100 … 204 °F` = `37.8 … 95.6 °C`,
установка `91 °F` = `32.8 °C` при текущих `33 °C`. Цель оказалась **ниже**
текущей температуры, нагрев считается выполненным мгновенно — отсюда и
короткий грев, и длинный писк «готово», и немедленный переход дальше.

Для клиента:

```
показать   = round((wireF - 32) / 1.8)     // из 0x15[0..2], 0x16[0]
отправить  = round(uiCelsius * 1.8 + 32)   // в 0x16
текущая    = payload0x00[3]                // уже °C
```

Проверить можно записью `0x16` со значениями `40 / 60 / 91 / 100 / 150 / 200 / 205`
и перечитыванием `0x15` — машина обрежет всё ниже `100` и выше `204`, если
считает в Фаренгейтах. Нагрев при этом включать не нужно.

## 7. Куда смотреть при отладке своего клиента

По убыванию вероятности, с опорой на то, что видно в коде:

1. **Логировать все кадры `0x00` целиком.** Состояние (байт 4) и ошибка
   (байт 5) в момент писка отвечают на вопрос сразу: `heatDone`/`heatBrewDone`
   — машина считает цикл завершённым; ненулевой байт 5 — отказ с конкретным
   кодом.
2. **Проверить, что `setTime` дошёл.** Это единственная команда, которую
   оригинал обязательно пишет до работы, и он даёт машине 300 мс после
   включения нотификаций, прежде чем её отправить. Клиент, который шлёт её
   сразу после `setNotifyValue`, может её потерять — запись идёт без
   подтверждения, потери никак не видно.
3. **Сверить единицы установки температуры** — см. §6. Цель ниже текущей
   температуры даёт мгновенное «готово»: короткий грев и длинный писк.
4. **Сверить второй байт `0x02`.** В командах таймера те же режимы
   пронумерованы иначе (`0x23`/`0x24` используют `PcmMode`, где 0 —
   нагрев+экстракция). Отправив в `0x02` нумерацию от таймера, вы попросите
   не тот режим: `0` в `0x02` — это только кипяток, без пролива.
5. **Сверить рабочие параметры.** Если перед стартом клиент писал `0x18`,
   проверить эхо (4 байта) — машина возвращает то, что реально приняла, с
   поправкой на свои границы из `0x17`.

Чего в этом списке нет и быть не может: «не хватает команды подтверждения».
Её в приложении нет.
